# First provisioning on Railway

Use a **new, unpublished template** for the counts service and private PostgreSQL database. These instructions are for an approved deployment; nothing creates a live service or changes Milo's production project on merge. Complete the [privacy checks](README.md) before allowing client traffic.

1. In **Workspace → Templates → New Template**, add a private Postgres service named `Postgres` with persistent storage and no public TCP proxy. Add the receiver from this repository with root directory `/hosted/counts`, its Dockerfile and healthcheck `/readyz`. Do not attach the website, settings editor or pairing relay.
2. In the **template composer's** Variables tab for the receiver, set the three service variables from [railway-template.variables.json](railway-template.variables.json). These are expressions, **not** credentials or a runtime env file. The database reference must point to the private connection URL for that database. Review the template before first deployment; do not paste the expressions into an already-running service or generate them in an entrypoint.
3. Deploy the template **once** to the intended environment. Railway's [template variable functions](https://docs.railway.com/templates/create#template-variable-functions) replace each `secret(...)` expression with a fresh random value when provisioning the template. This generates a 128-bit username and an independent 256-bit password. They are ordinary persistent **receiver service variables**: an authorized owner can reveal them under **counts service → Variables**. Restrict who can view those variables; don't export them, seal them against owner retrieval, or share them with the client, website or build jobs.
4. Use those values in the browser's HTTP authentication prompt over HTTPS. Do not put credentials in URLs or shell arguments. Check that a fresh unauthenticated browser cannot see stats, and that the same pair works after a normal redeploy and on each replica. A redeploy uses the saved variables; deploying the **template again** provisions a different service, not a rotation. The receiver has no fallback credentials, no Railway API token and no ability to update variables.

**Rotate explicitly.** In the receiver's service Variables, replace both values with independently generated values from a password manager (for example, 32 and 64 random lowercase hexadecimal characters). Stage both edits together, deploy all replicas, wait for old replicas to drain, and verify in private browser sessions that the old pair fails and the new pair works. Clearing either variable makes the receiver refuse to start. Reinstalling the service to recover a forgotten password is unnecessary: the authorized owner can retrieve it from Variables.
