# Separate the counts runtime login

This changes only the counts service and its dedicated PostgreSQL database. Do not run it on a shared database. Keep real client reporting off during the cutover. The bootstrap and migration owner belongs on the private database service, not in the receiver after cutover.

1. Deploy the compatible receiver first with its existing connection. As the migration owner, verify the two public aggregate tables exist, that no unrelated login uses this database, and that the role `milo_counts_receiver` does not exist anywhere in the cluster. Record the current database TEMP and public schema CREATE grants for rollback. The next step revokes these PUBLIC grants **on this database**. Do not apply if another login depends on them.
2. From a trusted operator session on the private DB, run [receiver-role.sql](scripts/receiver-role.sql) with psql connected to the counts database as the owner with role-administration privileges. The script is transactional, creates a **NOLOGIN** role, and fails rather than adopting an existing role. It grants only schema usage and SELECT, INSERT and the counter UPDATE columns on the two tables. No global logging settings change.
3. Use interactive psql `\password milo_counts_receiver` with a new random password from a secret manager; do not type a password into SQL, a command argument or a URL in the shell. Then run `ALTER ROLE milo_counts_receiver LOGIN`. Store a private connection string for this login in **counts → Variables → DATABASE_URL**, using the same private host, port and DB as before. Use protected input, not shared variables, shell arguments or logs. Do not change the database owner's credentials, database volume or the two dashboard variables.
4. Redeploy only counts. Verify the deployment succeeds, `/readyz` is ready, an unauthenticated dashboard returns 401, and an authenticated dashboard can read the existing totals. Do not test a write in production. Confirm the runtime's effective user and database match the restricted login and database, using a read-only session without printing the connection string. Confirm the former deployment has drained. Future schema changes run under the migration owner before deploying a receiver that needs them.
5. Rollback: leave reporting off and, if the receiver loses DB access, restore its previous private DB reference and redeploy only counts. Keep the volume and aggregate tables. Once restricted sessions drain, disable the new login; retaining it disabled is sufficient. If removing it, revoke its explicit grants in this DB, drop only this role, and restore only the PUBLIC grants actually present before the cutover. Do not drop a database or use a blanket ownership cleanup. The owner connection is an operational rollback, not privacy clearance to turn on reporting.

**Why scope logging by role and database?** Under PostgreSQL defaults, a constraint failure can print the failing row and SQL even with error bind logging disabled. The restricted login suppresses ordinary server messages below FATAL, disables statement/duration/sampling/bind logging, and omits SQL for ordinary errors. The HTTP response still signals a failed increment with a generic 503; readiness, deployment health and cluster diagnostics remain available. This is not a claim about authentication failures, FATAL/PANIC events, other logins, WAL, privileged live observation, or Railway edge logs. Recheck any added audit or tracing configuration.

**Retry limits:** each additional accepted delivery can add one more daily active and, if flagged, one new install and/or monthly active. Multiple deliveries can overcount repeatedly; the global limiter bounds throughput, not duplicates per client. No per-report or per-install ID is stored for deduplication.

Run the end-to-end check locally: `hosted/counts/scripts/pg-ephemeral.sh python3 hosted/counts/scripts/check-receiver-role.py`. It inspects only a throwaway cluster's log, comparing the same real HTTP failure before and after the role change, and verifies rollback, a successful write and the dashboard.
